Case Study 03

Payvice: a dashboard operations teams could actually trust

Payvice — payments dashboard

Industry

FinTech

Platform

Dashboard

Role

Product Design, Design Systems

Timeline

2022

Overview

Payvice is payments infrastructure for mid-sized merchants. I redesigned the operations dashboard used daily by finance and support teams to reconcile transactions, investigate disputes, and answer "why doesn't this number match."

The existing dashboard was functionally complete but emotionally exhausting to use — every discrepancy required cross-referencing three different views, and operations teams had started keeping their own spreadsheets as a workaround, which is its own kind of warning sign for a product built to be the source of truth.

The Challenge

Redesign a dense, data-heavy dashboard without simplifying away the precision that finance teams depend on. This was not a case for minimalism for its own sake — every number on screen had a reason to exist. The challenge was arranging that density so it could be trusted at a glance.

Context

I was brought in after the support team flagged that "why don't these numbers match" was their most common internal escalation. The dashboard wasn't wrong — it was just organized in a way that made discrepancies invisible until someone went looking for them.

Understanding the Users

I shadowed six operations specialists across two client companies through a full reconciliation cycle, timing every screen switch and noting every moment someone reached for a spreadsheet instead of the dashboard.

  • Users routinely opened three tabs to compare the same transaction across different views.
  • Status labels were technically accurate but used internal engineering terms unfamiliar to finance staff.
  • There was no single view that showed "what changed since yesterday," so every check started from zero.
I don't trust the dashboard until I've checked it against my spreadsheet. That's backwards, but that's where we are. — Operations specialist, merchant finance team

Research

A tab-switching audit showed the average reconciliation task required 14 view changes. Interviews confirmed this wasn't a training issue — the information architecture itself scattered related data across unrelated screens.

Research Finding
Every operations specialist we shadowed had built an informal personal system — a spreadsheet, a notes doc, a set of bookmarks — to compensate for the dashboard's fragmented structure.

Problem Definition

The dashboard needed to answer "has anything changed, and does it match" as a first-class question, not something users had to reconstruct manually from separate views.

Opportunity Statement

How might we design a dashboard that operations teams trust enough to retire their own spreadsheets?

Exploration

I prototyped a unified transaction record that pulled every related data point — payment status, dispute history, settlement timing — into one expandable view, replacing the three-tab pattern. We also tested a daily "what changed" summary as the dashboard's default landing view instead of a static totals page.

User Flows

The reconciliation flow was redesigned around a single entry point: land on what changed, drill into any transaction without leaving the page, resolve or flag it, return to the summary automatically.

User flow — daily reconciliation & discrepancy resolution

Wireframes

Early layouts tested a side panel for transaction detail against a full expand-in-place row. The expand-in-place pattern won because it preserved the surrounding context users relied on to spot patterns.

Low-fidelity wireframes — unified transaction record

Design Decisions

  • One record, not three views. Every related fact about a transaction lives in a single expandable row, so nothing requires a tab switch to verify.
  • Language finance teams actually use. We rewrote every status label in collaboration with support staff, replacing internal engineering terms with the vocabulary used on support calls.
  • "What changed" as the home screen. The dashboard now opens on a daily delta view rather than a static totals page, matching how the work actually starts each morning.

High Fidelity Designs

Density stayed high by design — this is a tool for people who read numbers all day — but a clearer type hierarchy and consistent status color coding made that density scannable rather than overwhelming.

High-fidelity UI — reconciliation dashboard & transaction detail

The redesigned daily summary and unified transaction record, in production.

Testing

We ran the new dashboard alongside the old one for four weeks with both shadowed teams. Every participant abandoned their personal spreadsheet workaround within the first two weeks of the new version.

Reflection

This project reshaped how I think about density. The instinct with data-heavy tools is often to simplify by hiding information; the real fix here was reorganizing information around the question users were actually asking, without removing a single data point they depended on.

Lessons Learned

  • When users build their own workaround system, that system is a research artifact — study it before redesigning anything.
  • Density isn't the enemy of clarity; fragmentation is.
  • Rewriting labels in a user's own vocabulary can outperform structural changes in perceived trust.
